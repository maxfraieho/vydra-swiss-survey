# Розділ 1. Навіщо SDD

## Проблема, яку вирішує SDD

Коли AI-агент (Claude, Codex, AGY) пише код напряму з розмовного промпту —
це називають **"vibe coding"**: ти описав ідею, агент згенерував код, ти
подивився — "виглядає ок" — і закомітив. Швидко для прототипу. Небезпечно
для продакшену:

- Немає письмового контракту, тому наступний агент (чи ти сам через
  тиждень) не знає, ЩО код мав робити — лише що він робить зараз.
- "Виглядає ок" (acceptance-by-observation) — не те саме що "перевірено"
  (acceptance-by-verification). Помилки в edge-case'ах непомітні на око.
- Архітектурні межі (hot path < 5ms, WAL SQLite, PII-політика) легко
  порушити ненавмисно, якщо агент про них не знає в момент генерації.
- Коли над одним проєктом працюють КІЛЬКА агентів (а в цьому проєкті —
  Claude Code, Codex CLI, AGY на трьох пристроях) — без спільного джерела
  правди кожен починає "з нуля", здогадуючись про контекст.

## Що робить SDD

Spec-Driven Development перевертає порядок: спочатку письмова специфікація
(`spec.md` — ЩО), потім план (`plan.md` — ЯК), потім задачі (`tasks.md` —
кроками), і лише тоді код. Специфікація — не документація ПІСЛЯ факту, а
контракт, з якого код генерується і проти якого перевіряється.

**Твоя роль як оператора змінюється:** ти більше не "пишеш промпт і
дивишся що вийде" — ти формулюєш намір у специфікації, а агент (будь-який
з трьох) реалізує його, дотримуючись контракту. Це повільніше на старті
фічі (треба написати spec.md), але швидше на дистанції: менше "а що це
взагалі мало робити?", менше регресій, менше розсинхронізації між агентами.

## Три рівні дисципліни (для довідки)

SDD-практика в цьому проєкті — не "все або нічого". Є градація:

- **Spec-First:** специфікація пишеться до коду, звіряється лише в кінці.
- **Spec-Anchored:** зміна spec АБО коду одразу тригерить перевірку —
  саме на цьому рівні працює `bin/sdd_verify.sh --gate` у проєкті зараз.
- **Spec-as-Source:** людина редагує лише spec, код генерується наново
  щоразу — найсуворіший рівень, у цьому проєкті не використовується.
