# Розділ 5. Передача контексту та ворота верифікації

Це найтехнічніший розділ книги, але саме він відповідає на питання "як
три різні агенти не заплутуються, працюючи над одним проєктом".

## Проблема: Context Drift

Уяви: вчора ти попросив Claude Code почати фічу через `/sdd:feature`,
він написав `spec.md` і `plan.md`, закомітив. Сьогодні ти хочеш
продовжити через Codex — але Codex не бачив вчорашньої розмови. Звідки
йому знати, що вже зроблено, а що ще ні? Якщо він почне "здогадуватись"
з коду — ризик розсинхронізації (Context Drift): він може повторити
роботу, або пропустити крок, або зробити припущення, яке суперечить
вчорашньому рішенню.

## Рішення: `.specify/feature.json`

Один файл, який завжди каже: яка фіча зараз активна, на якому кроці, на
якій гілці. Приклад реального вмісту (з фічі 021):

```json
{
  "feature_id": "021-multiagent-sdd-extension",
  "spec_dir": "specs/021-multiagent-sdd-extension",
  "branch": "astryx-ui-refactor",
  "phase": "implement",
  "phases_done": ["specify", "clarify", "plan", "tasks", "P2-skills"],
  "owner_agent": "claude-code",
  "host": "dev-184"
}
```

**Правило (записане в `AGENTS.md` як MUST):** перш ніж почати роботу,
агент читає цей файл + `git log -n 1 --stat`. Якщо `branch` у файлі не
збігається з поточною гілкою — агент ЗУПИНЯЄТЬСЯ і питає оператора,
замість того щоб діяти на здогад.

На кожному фазовому переході (specify→clarify→plan→tasks→implement→
verify) файл оновлюється і комітиться ОКРЕМИМ комітом (`spec:`, `plan:`,
`tasks:`, `impl:` префікс) — так наступний агент бачить не лише
поточний стан, а й точну історію переходів через `git log`.

## `bin/sdd_verify.sh` — три режими

### Без прапорців (default)

Проходить по ВСІХ `specs/*/` у репозиторії, перевіряє що кожна фіча має
хоча б один артефакт (`spec.md`/`plan.md`/`tasks.md`). Працює однаково
на будь-якій гілці — раніше скрипт мав хардкод-список із 32 конкретних
шляхів і падав, якщо запустити на гілці з іншим набором номерів specs
(наприклад, `master` не має `specs/020/`, а `astryx-ui-refactor` не має
`017`/`018`). Тепер — динамічний обхід, портативний між гілками.

### `--gate` — L3 Validator Gate

Перевіряє ЛИШЕ активну фічу (з `.specify/feature.json`): чи є всі
артефакти, потрібні для поточної фази. Наприклад, на фазі `plan` вимагає
`spec.md`+`clarify.md`+`plan.md`; на фазі `implement` — ще й `tasks.md`.
Це та команда, яку MUST запускати агент перед тим, як почати правити
код (записано в `AGENTS.md`).

```bash
bash bin/sdd_verify.sh --gate
```

Якщо чогось нема — падає з точним ім'ям відсутнього файлу, не просто
"помилка".

### `--arbiter` — LLM-суддя (SHADOW-режим)

Викликає `scripts/sdd_llm_judge.py`, який звіряє застейджений `git diff`
зі специфікацією через локальний LLM-проксі, перш ніж дозволити коміт.

**Статус (оновлено після P8, 2026-08-17):** написано, задеплоєно,
хук (`.githooks/pre-commit`) вже стоїть на кожному коміті — але працює в
**shadow-режимі**: пише вердикт у `logs/sdd_judge/`, НІКОЛИ не блокує
коміт, доки оператор свідомо не увімкне `SDD_JUDGE_SHADOW=0`. Живий факт:
перший же реальний коміт після встановлення хука зіткнувся з таймаутом
проксі (модель не відповіла за 15с) — хук коректно попередив і НЕ
заблокував коміт. Очікувана поведінка, не помилка.
`specs/021-multiagent-sdd-extension/tasks.md` T-149.

## Чому "fail-open", а не "fail-closed"

Якщо LLM-проксі тимчасово недоступний (нестабільне з'єднання Termux↔dev-184,
чи ключ невалідний) — арбітр НЕ блокує розробку, лише пише попередження
в лог і пропускає коміт. Свідоме рішення: краще пропустити одну
перевірку, ніж зупинити всю команду через інфраструктурний збій.
