# Розділ 6. Архітектура: три шари SDD

Цей розділ пояснює структуру, яку побачиш у `.specify/constitution.md`
§3, якщо відкриєш її сам. Три різні речі часто плутають між собою — цей
розділ розводить їх.

## Шар 1: Конституція (`.specify/constitution.md`) — інваріанти

Правила, які НІКОЛИ не можна порушити, незалежно від того, який агент чи
який native-інструмент викликається. Приклад: "hot path < 5ms",
"заборона push у master з dev-184". Це не процедура "як щось зробити" —
це межі, всередині яких будь-яка процедура має лишатись.

## Шар 2: Методологія (`docs/for-agents/sdd-development-methodology.md`) — процедура

ЯК саме виконати кожен тип задачі — 9 покрокових шаблонів (нова фіча,
багфікс, рефакторинг, інтеграція, навчання, дослідження, зняття
неоднозначностей, аудит spec-drift, верифікація). Це "рецепти", які всі
агенти читають ОДНАКОВО.

## Шар 3: Транспорт — як саме покликати процедуру

Тут з'являється розбіжність між агентами (Розділ 4): Claude Code кличе
через `/sdd:*`, Codex через `.codex/prompts/`, AGY — семантично через
`.agents/skills/`. Це просто РІЗНІ ДВЕРІ до однієї й тієї ж кімнати
(методології). Міняється лише механіка виклику, не зміст.

**Правило пріоритету**, записане прямо в конституції: якщо щось
суперечить — конституція виграє над методологією, методологія виграє над
конкретним транспортом. Ніхто не може обійти інваріант конституції,
просто покликавши команду по-іншому.

## Native Spec Kit — четвертий, паралельний шар

`specify-cli` (офіційний GitHub Spec Kit) встановлений у проєкті
(`specify integration install claude` + `codex`, 2026-08-17). Він додав:

- `.specify/templates/` — шаблони `spec.md`/`plan.md`/`tasks.md`/
  `constitution.md`/`checklist.md` (загальні, не проєкт-специфічні).
- `.specify/scripts/bash/` — допоміжні скрипти (`create-new-feature.sh`,
  `check-prerequisites.sh` тощо).
- `.claude/skills/speckit-*` та `.agents/skills/speckit-*` — 14
  офіційних upstream Agent Skills (specify/plan/tasks/clarify/
  constitution/analyze/checklist/converge/implement тощо).

**Важливо розуміти:** ці `speckit-*` скіли — ЗАГАЛЬНІ, написані для
будь-якого проєкту у світі, що використовує Spec Kit. Вони НЕ знають про
`hot path < 5ms` чи специфіку `vydra-swiss-survey` — цю специфіку знають
лише наші власні `sdd-*` скіли (Розділ 4) і сама конституція. Тому в
цьому проєкті обидва шари існують ПАРАЛЕЛЬНО: `speckit-*` — загальний
Spec Kit apparatus (для сумісності з екосистемою, майбутніх інтеграцій),
`/sdd:*` + `sdd-*` — проєкт-специфічна логіка з посиланнями на
конституцію.

### Історична деталь (для розуміння, чому так)

До 2026-08-17 конституція (§3) описувала команди `/speckit.specify` →
`/speckit.plan` → `/speckit.tasks` → `/speckit.implement`, які на той
момент **не існували фізично в репо** — ні `.specify/templates/`, ні
жодного `.claude/commands/speckit.*`. Це виявили живим SSH-аудитом перед
установкою `specify-cli`-інтеграцій. Після встановлення ці команди стали
Agent Skills (не буквальні слеш-команди), а конституція оновлена до
версії 1.1.0 з коректним поясненням. Якщо десь у старих джерелах (git
history, кеш пам'яті іншого агента) побачиш посилання на буквальний
`/speckit.specify`-виклик — це застаріла інформація.

## Практичний висновок

Тобі як оператору здебільшого досить Шару 2+3 (методологія + твій агент)
— Шар 1 (конституція) читаєш рідко, лише коли щось незрозуміло "чому
агент відмовився щось робити". Шар "native Spec Kit" — фонова
інфраструктура, з якою ти напряму не взаємодієш, якщо не плануєш
підключати ще одного нового агента в майбутньому.
