# Розділ 3. Креслення: Spec, Plan, Tasks, Конституція

Чотири документи, які ти вже бачив у Розділі 2 — тепер розберемо кожен
окремо.

## `spec.md` — ЩО (не ЯК)

Живе в `specs/<NNN-slug>/spec.md`. Відповідає на питання "що система
повинна робити", НЕ "як це реалізовано". Формат — user stories +
Given-When-Then сценарії + явний список того, що НЕ входить у скоуп
("Out of Scope" — важливо не менше за сам скоуп, запобігає повзучому
розширенню задачі).

Приклад реального файлу в цьому проєкті: `specs/021-multiagent-sdd-extension/spec.md`.

## `plan.md` — ЯК

Технічна стратегія реалізації + аналіз ризиків. Тут з'являються конкретні
файли, які будуть змінені, залежності між кроками, оцінка ризику кожного
кроку (LOW/MEDIUM/HIGH). У складних фічах `plan.md` включає емпіричну
перевірку поточного стану (не вигадувати, а SSH і подивитись, як зроблено
для 021-ї фічі — `plan.md` §0 там прямо таблиця "що перевірено, який
результат").

## `tasks.md` — Крок за кроком

Атомарні задачі з ідентифікаторами (`T-101`, `T-102`...), кожна — окремий
чекбокс `- [ ]`. Коли задача виконана, чекбокс стає `- [x]` і поруч —
ДОКАЗ виконання (файл:рядок, вивід тесту), не просто "зроблено". Це
навмисно негнучке правило: голослівні твердження неможливо перевірити,
докази — можна.

## `clarify.md` — Зняття неоднозначностей (опційно, але рекомендовано)

Якщо в плані є ≥3 архітектурних розвилки (варіант A чи B?), перед
`plan.md` варто пройти `clarify.md` — список явних питань + прийняті
рішення з обґрунтуванням. Приклад: `specs/021-multiagent-sdd-extension/clarify.md`
— 7 питань, кожне із секцією "Рішення" і "Обґрунтування".

## `.specify/constitution.md` — Незмінні правила проєкту

На відміну від `spec.md`/`plan.md` (які існують ПО ОДНОМУ на фічу),
конституція одна на весь проєкт. Містить:

- **Технологічний стек** — що є що (Flask backend, CDP browser control,
  SQLite WAL, React+Astryx frontend).
- **Фундаментальні інваріанти** — правила, які код НІКОЛИ не може
  порушити: PII-політика, hot path < 5ms, пріоритет людини-оператора над
  нейромережею (HITL), поріг N≥3 для промоції правил, заборона прямого
  push у `master` з dev-184.
- **Правила SDD Workflow** — сам факт, що проєкт використовує SDD, і як
  саме (розділ 6 цієї книги).

**Ієрархія пріоритету, коли щось суперечить:** конституція > методологія
(`docs/for-agents/sdd-development-methodology.md`) > конкретна команда
чи native-механізм виклику. Якщо `plan.md` фічі пропонує щось, що порушує
конституцію — конституція виграє, `plan.md` треба переписати.

## Одна пастка, на яку варто зважати

Native Spec Kit (`specify-cli`, встановлений у проєкті) генерує СВОЮ
конституцію-заглушку при ініціалізації в новому проєкті
(`.specify/templates/constitution-template.md`) — це загальний шаблон, не
плутай його з РЕАЛЬНОЮ конституцією проєкту в `.specify/constitution.md`.
Шаблон — для довідки/нових проєктів, не для редагування напряму.
