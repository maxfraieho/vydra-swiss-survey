# 0006. Застосувати fail-open стратегію для LLM pre-commit арбітра при інфраструктурних збоях

## Контекст і формулювання проблеми
У рамках Spec-Driven Development (SDD) та контролю конституційних інваріантів у проєкті впроваджено семантичний Git pre-commit хук `scripts/sdd_llm_judge.py`. Цей скрипт звертається до LLM-моделі для аналізу staged-змін на відповідність конституції та специфікаціям перед тим, як дозволити створення коміту.

У реальному середовищі розробки LLM-проксі (Aegis Relay / `dev-184`) піддається мережевим коливанням, тимчасовим сплескам затримок, перезавантаженням хоста або проблемам авторизації. Якщо арбітр реалізований за схемою *fail-closed* (блокувати коміт при будь-якій помилці зв'язку), будь-який інфраструктурний збій на стороні проксі миттєво паралізує роботу інженера: стає неможливо зберегти локальну роботу, зафіксувати хотфікс або перемкнути гілку.

Необхідно було визначити політику поведінки pre-commit арбітра при недоступності віддаленого бекенда моделі.

## Рушії рішення
- **Безперервність процесу розробки (Developer Velocity & DX)**: локальні Git-операції не повинні залежати від наявності зовнішнього зв'язку або аптайму експериментальних LLM-серверів.
- **Емпірична стійкість до збоїв**: захист від хибних блокувань (false rejections) під час зафіксованих аварій та перезавантажень проксі-хоста `dev-184`.
- **Семантична точність**: блокування коміту повинно відбуватися ВИКЛЮЧНО на основі усвідомленого та явно отриманого вердикту `FAIL` від моделі, яка успішно проаналізувала diff.

## Розглянуті варіанти
1. **Fail-closed підхід**: блокувати `git commit` (exit code 1) при будь-якій мережевій чи інфраструктурній помилці виклику арбітра.
2. **Блокуючий retry-loop з обов'язковим очікуванням**: повторювати запити до відновлення зв'язку з проксі.
3. **Fail-open підхід з попередженням (Skip on Infrastructure Error) (Обраний)**.

## Підсумок рішення
Обрано **Варіант 3: Fail-open підхід (shadow/advisory skip при збоях інфраструктури)**, реалізований у `scripts/sdd_llm_judge.py`.

У функції `call_judge` реалізовано перехоплення системних та мережевих винятків (`URLError`, `TimeoutError`, `OSError`). Якщо виклик до проксі не може бути завершений з будь-якої інфраструктурної причини, функція виводить попередження `_warn()`, повертає `None`, а викликаючий процес пропускає перевірку без блокування коміту.

Блокування коміту (exit code 1) відбувається виключно тоді, коли арбітр успішно повернув валідну JSON-відповідь зі статусом `verdict == "FAIL"`.

```python
# scripts/sdd_llm_judge.py
def call_judge(prompt: str, url: str, key: str, model: str, timeout: int = 45) -> dict | None:
    """Returns a parsed verdict dict, or None if the call could not be
    completed for any infrastructure reason (caller must treat None as
    'skip, do not block')."""
    ...
    except (urllib.error.URLError, TimeoutError, OSError) as e:
        _warn(f"judge endpoint unreachable ({e}) — skipping, not blocking")
        return None
```

Цей принцип також узгоджується з патерном `arbiter_mode: shadow` у шаблоні `sdd-universal-template` (T-330), де автоматичні LLM-арбітри за замовчуванням не блокують пайплайн за відсутності високої впевненості або стабільного зв'язку.

### Наслідки
- **Позитивні**:
  - Розробник ніколи не опиняється заблокованим через проблеми локальної мережі, таймаути (наприклад, початковий ліміт 15с або перевантаження моделі) чи ребут `dev-184`.
  - Відсутність фальшивих блокувань під час польової чи автономної розробки без інтернету.
  - Збереження строгого контролю: якщо модель доступна і виявила порушення конституції — коміт надійно відхиляється.
- **Негативні**:
  - Теоретична можливість пропуску дефекту в репозиторій, якщо коміт зроблено саме в момент падіння проксі (компенсується вторинними перевірками в CI або ручним код-рев'ю).

## Плюси і мінуси варіантів

### Варіант 1: Fail-closed підхід
* Добре: максимальна строгість — жоден рядок коду не потрапить у репозиторій без цифрового підпису LLM-арбітра.
* Погано: повний параліч розробки при найменшому збої мережі чи оновленні сервера; вимушене масове використання прапорця `--no-verify`, що нівелює цінність хуків взагалі.

### Варіант 2: Блокуючий retry-loop
* Добре: гарантує спробу дочекатися відповіді арбітра.
* Погано: створює непередбачувані затримки при виконанні звичайного `git commit`; зависає нескінченно при тривалому даунтаймі бекенда.

### Варіант 3: Fail-open підхід (Обраний)
* Добре: захищає продуктивність розробника та детермінізм Git-воркфлоу.
* Добре: блокує коміт тільки за наявності змістовного аргументованого `FAIL`.
* Добре: емпірично перевірений та довів свою стійкість під час реальних інцидентів з доступністю `dev-184`.
* Погано: вимагає дисципліни в CI для вилову змін, що пройшли повз арбітра під час збою.
