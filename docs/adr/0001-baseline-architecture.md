# 0001. Базова архітектура vydra-swiss-survey (ретроактивна фіксація)

## Контекст і формулювання проблеми

Проєкт `vydra-swiss-survey` розвивався органічно до впровадження ADR-шару
(022). Кілька фундаментальних технологічних рішень уже прийняті й глибоко
вкорінені в коді, але ніде явно не задокументовані з альтернативами й
причинами. Цей ADR — не запис реальної дискусії в момент вибору (її не
було зафіксовано), а свідома ретроактивна фіксація поточного стану
(`clarify.md` п.7, принцип "Baseline, не архівна реконструкція"): щоб
AI-агенти в майбутньому не намагались "порефакторити" ці рішення, не
розуміючи вихідних обмежень.

## Рушії рішення

* Автоматизація живе на Termux (Android) як основне цільове середовище —
  важкі рантайми (JVM, повноцінний браузерний драйвер-стек) небажані.
* Hot path (`get_host_rules`, `bump_rule_outcome`) має лишатись < 5мс
  (Інваріант 2 конституції) — синхронний, легкий стек без ORM-накладних
  витрат.
* Одноосібний оператор + AI-агенти як основні "користувачі" системи, не
  команда розробників — простота дебагу й локальний детермінізм важливіші
  за горизонтальну масштабованість.

## Розглянуті варіанти

* Flask 3.x (синхронний) — обрано
* FastAPI/async-стек — не обрано
* SQLite 3 + WAL режим — обрано
* PostgreSQL/інша клієнт-серверна СУБД — не обрано
* Прямий Chrome DevTools Protocol (CDP) через WebSocket — обрано
* Selenium/Playwright (повноцінний драйвер-стек) — не обрано
* React 19 + власна дизайн-система Astryx (`@astryxdesign/core`) — обрано
* Готовий UI-кіт (Material/Ant/shadcn без кастомізації) — не обрано

## Підсумок рішення

Обрано **Flask 3.x + прямий CDP + SQLite WAL + React/Astryx**, тому що
разом ці вибори мінімізують рантайм-вагу на Termux, зберігають
детермінізм hot path без мережевого/процесного оверхеду клієнт-серверної
СУБД, і уникають залежності від важких драйвер-бінарників
(`chromedriver`/`geckodriver`), яких на Android-хості або немає, або вони
нестабільні.

### Наслідки

* Добре, тому що: нуль зовнішніх системних процесів для персистентності
  (SQLite — файл, не сервіс) і для браузерного керування (CDP —
  вбудований у сам Chrome/Chromium, WebSocket без посередника).
* Добре, тому що: синхронний Flask спрощує трасування помилок в
  одноосібному деплої — немає async-специфічних гонок стану в тому самому
  процесі, що обслуговує hot path.
* Погано, тому що: SQLite WAL не масштабується на кілька одночасних
  writer-процесів без ризику `database is locked` — прийнятно зараз (один
  writer), стане обмеженням якщо з'явиться потреба в кількох паралельних
  survey-агентах на одному профілі.
* Погано, тому що: прямий CDP-протокол крихкіший за абстракцію
  Selenium/Playwright при змінах у Chrome DevTools API між версіями
  браузера — свідомо прийнятий ризик заради відсутності важкої залежності.

## Плюси і мінуси варіантів

### FastAPI/async-стек

* Добре, тому що: кращий throughput під конкурентним навантаженням.
* Погано, тому що: конкурентність не потрібна для одного survey-агента на
  профіль — складність async без вигоди.

### PostgreSQL/клієнт-серверна СУБД

* Добре, тому що: справжня конкурентна запис-безпека, репліковані бекапи.
* Погано, тому що: окремий сервісний процес на Termux — операційний
  overhead без відповідної потреби на цьому масштабі.

### Selenium/Playwright

* Добре, тому що: стабільніший, версійно-незалежний API поверх CDP.
* Погано, тому що: важкі бінарні залежності (driver-менеджери), погано
  сумісні з Android/Termux середовищем.

### Готовий UI-кіт без кастомізації

* Добре, тому що: швидший старт, менше власного коду для підтримки.
* Погано, тому що: не відповідав вимогам візуальної ідентичності
  (Astryx design system розроблена окремо, `specs/011-013`).
