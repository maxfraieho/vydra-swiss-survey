# 0004. Забезпечити абсолютний пріоритет оператора (HITL Precedence) із синхронною санітаризацією крихких селекторів

## Контекст і формулювання проблеми
Під час автоматизованого проходження опитувань автономна Vision-модель (Gemma Vision) або автономний евристичний рушій можуть зайти у глухий кут: зіткнутися з нестандартними UI-компонентами (shadow DOM, canvas-слайдери, динамічні SVG-матриці), зациклитися або зробити хибний вибір. Для вирішення таких ситуацій необхідний механізм прямого втручання людини-оператора (Human-in-the-loop, HITL).

Однак виникає супутній критичний ризик: коли оператор вручну вказує селектор або правило переходу під час живої сесії, він схильний використовувати швидкі, але крихкі позиційні евристики (наприклад, `item30`, `every-3rd`, `option[2]`, `nth-child(4)`). Потрапляння таких позиційних селекторів у базу знань без попередження веде до деградації системи при найменшій зміні верстки чи порядку варіантів у наступних опитуваннях.

Необхідно було об'єднати абсолютний авторитет рішень оператора над AI з автоматичним запобіжником, який блокує ненавмисне додавання крихких селекторів безпосередньо на точці входу.

## Рушії рішення
- **Інваріант 3 Конституції (HITL Precedence)**: рішення та ручні оверрайди оператора мають безумовний 100% пріоритет над прогнозами Vision/LLM моделей.
- **Інваріант 6 Конституції (Санітаризація евристик)**: позиційні та крихкі патерни повинні бути перехоплені до потрапляння в пам'ять.
- **Синхронний зворотний зв'язок**: оператор повинен отримувати миттєве попередження (HTTP 422) у прямому інтерфейсі управління без розриву активної сесії опитування.
- **Можливість усвідомленого підтвердження**: збереження за оператором права форсувати позиційне правило за наявності вагомих причин через явний прапорець `confirm_positional: true`.

## Розглянуті варіанти
1. **Повна довіра Vision-моделі без ручного оверрайду (Unconstrained Autonomous Vision)**.
2. **Вільний HITL-оверрайд без валідації (Unchecked Manual Overrides)**.
3. **Асинхронна черга постобробки та модерації евристик**.
4. **Синхронний HITL-ендпоінт із inline Regex-санітаризацією та HTTP 422 Gate (Обраний)**.

## Підсумок рішення
Обрано **Варіант 4: Синхронний HITL-ендпоінт з inline Regex-санітаризацією та HTTP 422 Gate**, реалізований у `astryx_survey_server.py:1125-1155` на ендпоінті `POST /api/survey/override_step`.

Рішення уніфікує Інваріант 3 та Інваріант 6 в єдиній точці входу:
1. **HITL Precedence (Інваріант 3)**: будь-який валідний запит оператора негайно перериває автономний цикл і застосовує вказану дію до браузера через CDP.
2. **Positional Guard (Інваріант 6)**: якщо поле `target` містить патерни позиційної крихкості (`every-\d+`, `item\d+`, `nth-child`, `option\[\d+\]`), сервер відмовляє у збереженні з HTTP 422 `positional_heuristic_detected`, доки клієнт не надішле явне підтвердження `confirm_positional: true`.

```python
# astryx_survey_server.py:1125-1155
@app.route("/api/survey/override_step", methods=["POST"])
def override_step_api():
    ...
    if target:
        POSITIONAL_RE = re.compile(
            r'(every-\d+|item\d+|nth-child|every\s+\d+|option\[\d+\])',
            re.IGNORECASE
        )
        confirm_positional = data.get("confirm_positional", False)
        rule_val = f"{target} ({explanation})" if explanation else target
        if POSITIONAL_RE.search(rule_val) and not confirm_positional:
            return jsonify({
                "error": "positional_heuristic_detected",
                "message": "Виявлено позиційний селектор (наприклад, nth-child, itemN, every-N). Позиційні правила крихкі до змін верстки і потребують явного підтвердження.",
                "requires_confirmation": True,
            }), 422
```

### Наслідки
- **Позитивні**:
  - Оператор має гарантований важіль перехоплення керування у складних сценаріях, усуваючи зациклення моделі.
  - База правил захищена від випадкового засмічення крихкими селекторами.
  - Інтерактивний UI (Astryx React) отримує чіткий контракт: при коді 422 відображається модальне діалогове вікно підтвердження оператора.
- **Негативні**:
  - Потребує додаткового клієнтського коду для обробки 422 та відправки повторного запиту з `confirm_positional: true`.

## Плюси і мінуси варіантів

### Варіант 1: Повна довіра Vision-моделі без ручного оверрайду
* Добре: 100% автономність, відсутність потреби у користувацькому інтерфейсі оверрайду.
* Погано: повний параліч при невідомих UI-патернах; опитування провалюються без можливості порятунку сесії.

### Варіант 2: Вільний HITL-оверрайд без перевірки селекторів
* Добре: мінімальна кодова база ендпоінта, швидке збереження без зайвих запитів.
* Погано: швидка деградація бази знань; позиційні селектори на кшталт `nth-child(2)` потрапляють у `shadow`, а згодом активуються і ламають сусідні опитування.

### Варіант 3: Асинхронна черга модерації
* Добре: оператор вводить дані, а система у фоні перевіряє селектори.
* Погано: розриває синхронний flow опитування; сторінка в браузері очікує негайної дії, асинхронність тут неприйнятна.

### Варіант 4: Синхронний HITL + Regex 422 Gate (Обраний)
* Добре: миттєве виконання оверрайду з гарантованим захистом пам'яті.
* Добре: повністю задовольняє вимоги Інваріантів 3 та 6.
* Погано: додає мікрозатримку на взаємодію з UI у разі навмисного позиційного вибору.
