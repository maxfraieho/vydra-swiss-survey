# 0003. Встановити строгий трифакторний gate (N≥3 унікальних прогонів) для авто-промоції shadow-правил

## Контекст і формулювання проблеми
У проєкті `vydra-swiss-survey` знання про взаємодію з опитувальними платформами акумулюються у формі селекторних та евристичних правил (`host_rules` у SQLite базі знань). Під час виконання сесій автономний агент генерує нові евристики, які спочатку створюються у статусі `shadow` (спостережний режим). У цьому режимі правила оцінюються безпосередньо в ході прогонів, накопичуючи лічильники успіхів (`wins`) та невдач (`losses`).

Виникла проблема визначення критерію переведення правила зі статусу `shadow` в активний робочий статус `active`. Якщо активувати правила занадто рано, виникає ризик перенавчання (overfitting) на одиничних нестандартних сторінках, помилкових спрацьовувань (false positives) або засмічення пам'яті артефактами разових збоїв. Якщо ж вимагати виключно ручного підтвердження людиною, система втрачає автономну здатність до самонавчання у масштабованих тривалих прогонах.

## Рушії рішення
- **Захист від перенавчання на аномальних сесіях**: виключення активації евристик, які випадково спрацювали лише в межах одного специфічного або дефектного прогону.
- **Стійкість до повторних запусків (Replay Immunity)**: запобігання штучній накрутці метрик правила багаторазовим перезапуском одного й того самого `run_id`.
- **Статистична надійність успіху**: правило має демонструвати переважну ефективність над невдачами з суттєвим запасом маржинальності.
- **Дотримання Інваріанту 4 Конституції проєкту**: централізований детермінований шлях промоції без розмазування бізнес-логіки по кодовій базі.

## Розглянуті варіанти
1. **Миттєва промоція після першого успіху (N=1, Greedy Promotion)**.
2. **Простий сумарний лічильник успіхів (wins ≥ 3) без валідації контексту сесій**.
3. **Виключно ручна промоція оператором (Human-in-the-loop Gate)**.
4. **Трифакторний SQL-гейт з валідацією N≥3 унікальних успішно завершених прогонів (COUNT DISTINCT run_id)**.

## Підсумок рішення
Обрано **Варіант 4: Трифакторний SQL-гейт з валідацією N≥3 унікальних завершених сесій**, реалізований у функції `auto_promote_rules(min_unique_runs: int = 3)` у `persona_graph_memory.py:599-625`.

Промоція виконується атомарним SQL-запитом, який вимагає одночасного виконання трьох суворих математичних умов:
1. `wins >= min_unique_runs` (мінімальний поріг успішних застосувань, за замовчуванням 3).
2. `wins > (losses * 2)` (строге переважання успіхів над невдачами мінімум у 2 рази, що відсікає нестабільні або випадкові селектори).
3. `(SELECT COUNT(DISTINCT run_id) FROM rule_applications WHERE rule_applications.rule_id = host_rules.id AND LOWER(outcome) = 'completed') >= min_unique_runs` (підтвердження відтворюваності щонайменше у 3 абсолютно різних завершених сесіях опитування).

```python
# persona_graph_memory.py:599-625
def auto_promote_rules(min_unique_runs: int = 3) -> int:
    """Promotes shadow rules to active ONLY if they are confirmed across
    at least min_unique_runs distinct completed runs in rule_applications."""
    conn = _connect()
    try:
        now_str = _now()
        cur = conn.execute(
            """
            UPDATE host_rules
            SET status = 'active', updated_at = ?
            WHERE status = 'shadow'
              AND wins >= ?
              AND wins > (losses * 2)
              AND (
                  SELECT COUNT(DISTINCT run_id)
                  FROM rule_applications
                  WHERE rule_applications.rule_id = host_rules.id
                    AND LOWER(outcome) = 'completed'
              ) >= ?
            """,
            (now_str, min_unique_runs, min_unique_runs)
        )
        promoted_count = cur.rowcount
        conn.commit()
        return promoted_count
    finally:
        conn.close()
```

Ця функція викликається детерміновано з `bump_rule_outcome()` (`persona_graph_memory.py`), реалізуючи Інваріант 4 Конституції проєкту.

### Наслідки
- **Позитивні**:
  - Нульовий ризик закріплення хибних селекторів, спричинених одиничними DOM-мутаціями або некоректними відповідями AI.
  - Повна стійкість до циклічних ретраїв: якщо той самий `run_id` генерує 10 викликів, `COUNT(DISTINCT run_id)` зараховує його рівно як 1 прогін.
  - Автоматична самоочистка бази знань: правила з високим рівнем невдач блокуються умовою `wins > losses * 2` і залишаються в тіні назавжди або до видалення.
- **Негативні**:
  - Затримка «холодного старту»: новому правилу потрібно пройти як мінімум 3 повноцінних окремих опитування, перш ніж стати активним.
  - Більш складний SQL-запит із підзапитом до таблиці `rule_applications`.

## Плюси і мінуси варіантів

### Варіант 1: Миттєва промоція (N=1)
* Добре: швидка адаптація під нові домени вже з першого кроку.
* Погано: критичний рівень false-positive; випадковий селектор ламає наступні прогони; катастрофічне перенавчання на аномаліях.

### Варіант 2: Простий сумарний лічильник (wins ≥ 3 без DISTINCT run_id)
* Добре: проста реалізація без підзапитів та зв'язку з `rule_applications`.
* Погано: вразливість до ретраїв — один зациклений прогін, що повторив крок 3 рази, миттєво активував би неперевірене правило.

### Варіант 3: Виключно ручна промоція оператором
* Добре: 100% людський контроль над кожним селектором у базі.
* Погано: блокує автономну роботу на Termux/мобільних нодах; вимагає постійної присутності оператора; не масштабується.

### Варіант 4: Трифакторний SQL gate N≥3 (Обраний)
* Добре: поєднує статистичну впевненість (`wins > 2*losses`), поріг накопичення (`wins >= 3`) та крос-сесійну валідацію (`DISTINCT run_id >= 3`).
* Добре: повністю відповідає Інваріанту 4 Конституції.
* Погано: повільніше входження нових евристик у бойовий режим (виправданий трейдофф заради стабільності).
