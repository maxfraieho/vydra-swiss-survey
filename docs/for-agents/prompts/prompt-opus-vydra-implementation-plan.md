# Промт для Opus: план реалізації покращень Vydra Swiss Survey Agent

## Роль

Ти — старший інженер, що робить **план реалізації**, а не пишеш код. Це промт для планувальної фази: результат — документ з фазами, файлами, задачами та ризиками, який людина зможе review'ити, а потім вручну перетворити на промти для `agy` (агента-виконавця). Не генеруй повноцінний код у відповіді — тільки план, і там, де потрібно, короткі сигнатури/псевдокод для ілюстрації підходу.

## Контекст

Є звіт-дослідження (додається нижче, розділ "Джерело дослідження") з рекомендаціями щодо покращення проєкту `vydra-swiss-survey` — агента для проходження опитувань через CDP + vision-модель. Дослідження робив Gemini **без доступу до поточного стану кодової бази** — воно не знало, що частина запропонованого вже реалізована в попередніх фазах цієї ж роботи, і в двох місцях пропонує вигадані числові пороги без емпіричного обґрунтування.

Я вже зробив рев'ю дослідження і визначив, що і в якому порядку варто робити. Твоя задача — перетворити це рев'ю на конкретний план реалізації, **починаючи з верифікації проти реального коду**, а не сліпо йти за роадмап-таблицею дослідження.

## Фаза 0 (обов'язкова, перед усім іншим): верифікація стану коду

Перш ніж планувати будь-яку задачу, перевір і зафіксуй у плані відповіді на:

1. Чи існує `reflection._find_phrase()` і тест `test_cdp_diacritics_handling.py`? Що саме вони роблять — нормалізують текст сторінки чи шукають DOM-елемент? Це той самий шар, що дослідження пропонує як нову `normalize_survey_text`/`find_best_dom_element` у `cdp_client.py`, чи інший (сумісний) шар?
2. Чи існує `async_review_queue` (Task 1–9) і таблиця для нього? Дослідження описує "Async Failure Review Queue" так, ніби її ще нема (`review_queue`) — це дублікат чи інша назва того самого?
3. Чи є в БД таблиця `providers`, і в якому стані ізоляція правил за scope (порожня таблиця чи ні)?
4. Чи існує вже інтеграція з Telegram (у зв'язку з "Черга опитувань з Telegram" в Ops), яку можна перевикористати для `notify_tutor_captcha_blocking()`?
5. Який зараз реальний гейт промоції правил (`N ≥ 3`) і чи він покритий тестами?

Для кожного пункту в плані має бути явний висновок: "існує і сумісне", "існує і дублює — не створювати заново", або "не існує — створювати з нуля".

## Пріоритети та скоуп (мій відкоригований порядок — дотримуйся його, не порядку з таблиці дослідження)

**P1. Діакритика/нормалізація тексту (найвищий пріоритет)**
Пряма фіксація бага (`intensité`/`intensite`), низький ризик, не чіпає БД. NFD-декомпозиція + мапа умляутів + Jaro-Winkler. Перед реалізацією — розв'язати п.1 з Фази 0: об'єднати з `reflection._find_phrase()` чи ні.

**P2. HITL friction — частково**
- Visual overlay з bounding boxes (`boundingClientRect` + SVG-шар у `SurveyOps.tsx`) — реалізовувати, спирається на вже підтверджений принцип deterministic targeting.
- Контекстні підказки на основі `TOPIC_KEYWORDS` — реалізовувати, словник патернів реальний.
- "Async Failure Review Queue" — **не створювати нову чергу**. Якщо Фаза 0 підтвердить, що `async_review_queue` вже існує, задача тут — інтеграція/розширення наявної черги під нові потреби UI, а не нова паралельна структура.

**P3. Ізоляція правил — тільки 4-рівнева ієрархія, БЕЗ математики впевненості**
Реалізувати `EXACT_LAYOUT → PROVIDER_PATTERN → HOST_PATTERN → GLOBAL_PATTERN` та механізм `structure_hash` (фінгерпринт DOM-розмітки). Це закриває реальну прогалину (порожня/неповна таблиця `providers`).
**Явно виключити зі скоупу:** інтервал Вілсона (`wilson_lower ≥ 0.70`), Бета-біноміальну модель з часовим згасанням (`λ=0.05/день`), ентропійний поріг (`entropy ≤ 0.35`), співвідношення `W_eff/L_eff ≥ 5.0`. Це невигадані-математично, але емпірично невалідовані пороги "зі стелі" на масштабі даних (десятки правил, 2 персони), де складність не виправдана. Залишити наявний робочий гейт `N ≥ 3`. Якщо в майбутньому знадобиться калібрування — це окрема задача з збором даних, не частина цього плану.

**P4. CoT-промпт для Gemma 3 4B Vision**
Дешево і безпечно: тільки зміна тексту системного промпту під zero-hallucination CoT (JSON-структура: visual_analysis → persona_matching → decision). Без змін схеми БД чи гарячого шляху.

**P5. Self-healing — останнім, частково**
- Детекція капчі через пошук підрядків (`cf-turnstile`, `g-recaptcha` тощо) — прийнятний MVP, зафіксувати в плані як **відому обмеженість** (хибні негативи на капчах без цих ключових слів).
- Новий стан `survey_session_state` — реальне розширення схеми, вища складність, планувати окремо з міграцією і rollback-планом.
- `notify_tutor_captcha_blocking()` — **перевикористати наявну Telegram-інтеграцію**, якщо Фаза 0 п.4 підтвердить її існування; не будувати нову з нуля.

## Що ігнорувати з дослідження

Роадмап-таблиця дослідження містить сміттєві артефакти конвертації цитат (`[span_33](start_span)[span_33](end_span)` тощо) — не переносити їх у код, специфікації чи назви задач буквально.

## Формат відповіді

Видай план у форматі Markdown зі структурою:

1. **Висновки Фази 0** (верифікація, по кожному з 5 пунктів)
2. **План по фазах P1–P5**, для кожної фази:
   - Файли, що зачіпаються
   - Конкретні задачі (як список, без коду)
   - Залежність від Фази 0 (якщо є)
   - Ризик і план відкату
   - Критерій готовності (як перевірити, що зроблено правильно)
3. **Явно виключено зі скоупу** — окремим блоком, з коротким обґрунтуванням чому

Не пиши код реалізації — тільки план. Псевдокод/сигнатури допустимі лише як ілюстрація там, де без них незрозуміло, що саме мається на увазі.
