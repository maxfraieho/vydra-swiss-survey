## Промт (вставити в `eclaude` на Oracle)

Ти — дослідник-архітектор Feature 022 у репо vydra-swiss-survey, гілка astryx-ui-refactor. Запущений через eclaude на Oracle (Aggy-proxy). Працюй у режимі read-heavy: спершу дослідження, потім мінімальний рефакторинг зі збереженням поведінки.

### 0. Підготовка (обов'язково перед аналізом)

Онови індекс gitnexus до актуального стану і використай його як основне джерело навігації по коду (не грепай усе вручну): `gitnexus index --update`. Індекс доступний через Tailscale з dev .184 — якщо локально його немає, звернись до .184 і працюй з віддаленим індексом.

`git fetch --all && git checkout astryx-ui-refactor && git pull`.

Прочитай `docs/astryx-refactor/*.md` (плани 020/021/021B/021C і claude-audit-*). Не переробляй те, що вже закрито гейтами.

### 1. Дослідження — Пайплайн A: НАВЧАННЯ (knowledge acquisition)

Питання, на які потрібні відповіді з file:line:

- Звідки беруться знання: browser sources, AI sources, personas, patterns, hosts?
- Як сирий трейс перетворюється в правило (rule)? Хто пише, хто валідує, де конфлікти?
- Де рішення приймає людина, а де модель? Скільки кроків HITL на одне правило?
- Що зберігається між прогонами, а що втрачається (in-memory, файли, БД)?
- Які виклики LLM ідуть через проксі, з якими промтами, і чи є кешування/дедуп.

Вихід: карта потоку (ASCII), таблиця «крок → код → сховище → хто вирішує».

### 2. Дослідження — Пайплайн B: ВИКОНАННЯ (autonomous survey run)

- Повний шлях: launch → навігація → auth → заповнення → submit → outcome.
- Де саме агент зупиняється і чекає людину (waiting_auth, waiting_verification)?
- Які з цих зупинок ПРИНЦИПОВІ (капча, 2FA), а які — наслідок слабких правил або відсутньої пам'яті? Це головне питання дослідження.
- Які кроки не мають retry/recovery і валять весь прогон.
- Чи використовуються знання з пайплайну A під час прогону — чи агент щоразу «вчиться заново»? Дай доказ з коду.

Вихід: перелік точок відмови з класифікацією [непереборне людське] / [лікується правилом] / [лікується пам'яттю] / [баг].

### 3. Synapse — зовнішня пам'ять агентів

Контекст: Synapse була реалізована на смартфоні .196 (пристрій вийшов з ладу), на dev .184 реалізації немає. Мета власника — багато агентів на різні сайти/задачі зі СПІЛЬНОЮ пам'яттю: взаємопідміна і групова робота.

Завдання:

- Знайди в git history сліди старої інтеграції Synapse (`git log --all -S synapse -i`, гілки, видалені файли) і відтвори контракт: які операції, який формат записів.
- Спроектуй мінімальний інтеграційний шар для .184:
  - схема запису: `{agent_id, site/host, task_type, situation, action, outcome, confidence, ts}`
  - операції: `write(experience)`, `search(situation) → top-k`, `promote(experience → rule)`
  - розділення scope: private (per-agent) / shared (cross-agent), щоб один агент не отруював базу іншим доменом.
- Дай ЧЕСНУ оцінку: що дає Synapse проти простого спільного сховища правил у БД. Якщо виграш малий — так і напиши, з аргументами. Не проектуй те, що не потрібно.

Вихід: `docs/astryx-refactor/sdd-022-synapse.md` з Problem/Decision/Implementation/Gates. Код інтеграції — тільки за окремим підтвердженням координатора.

### 4. Рефакторинг (обмежений, без зміни поведінки)

Дозволено тільки те, що прямо випливає з розділів 1–2:

- виділити явні межі між пайплайнами A і B (модулі/інтерфейси замість наскрізних викликів);
- зробити стан прогону явним (одна машина станів, а не розсипані прапорці);
- прибрати дублювання LLM-викликів і додати кеш там, де промт детерміністичний.

ЗАБОРОНЕНО: переписувати UI (закрито в 020/021), змінювати схему БД без SDD, трогати auth/секрети, «косметичні» масові перейменування.

### Verification Gates (кожен = команда + очікуваний вивід + PASS/FAIL)

- **G0**: gitnexus індекс оновлено — команда + кількість проіндексованих файлів.
- **G1**: карта пайплайну A має ≥1 file:line на кожен крок. Немає «ймовірно».
- **G2**: карта пайплайну B має ≥1 file:line на кожну точку відмови + класифікацію.
- **G3**: доказ (код або лог), чи знання з A реально читаються в B. PASS = однозначна відповідь.
- **G4**: Synapse — контракт із history відтворено АБО доведено, що слідів немає (git-вивід).
- **G5**: після рефакторингу — `bash bin/ui_verify.sh`; `bash bin/deploy_verify.sh`; `bash bin/ops_verify.sh` → усі exit 0. UI-інваріанти не зросли: `rg '#[0-9a-fA-F]{3,8}' src/ | wc -l == 0`; `rg 'style={{' src/ | wc -l <= 17`.
- **G6**: живий прогон одного опитування ДО і ПІСЛЯ рефакторингу — однакова кількість кроків і однаковий outcome. Зміна поведінки = FAIL.

### Правила

- Один FAIL = не «100% PASS». FAIL + план виправлення.
- Секрети (Oracle, proxy, Telegram) не комітити — лише env/ssh-агент, у документах маскувати.
- Коміти з префіксом `022:` у гілку `astryx-ui-refactor`.

Здача: `docs/astryx-refactor/claude-audit-022.md` — Гейт → команда → вивід → PASS/FAIL. Плюс `sdd-022-pipelines.md` і `sdd-022-synapse.md`.
