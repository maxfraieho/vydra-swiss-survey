## Деталі

### G0 — FAIL

Три незалежні шляхи оновлення індексу перевірено, усі закриті:

1. `node .gitnexus/run.cjs analyze` — каталогу `.gitnexus/` у репозиторії немає.
2. `npx gitnexus analyze` — вихід у мережу закритий.
3. MCP-інструменти (`mcp__gitnexus__list_repos`, `impact`, `detect_changes`) — дозвіл не наданий.

**Наслідок, що виходить за межі самого гейта.** `CLAUDE.md` містить безумовне правило:

> NEVER edit a function, class, or method without first running `impact` on it.

Обов'язкову передумову будь-якого редагування виконати неможливо, тому **код розділу 4 у цій
сесії не писався**. Замість коду підготовлено повну специфікацію рефакторингу (R1–R3) у
`sdd-022-pipelines.md`, готову до застосування там, де gitnexus доступний.

### G2 — PASS

§2.2 — таблиця точок зупинки на людину; §2.3 — 20 точок відмови з класифікацією.

Розподіл: **[непереборне людське]** — 2 (капча; перший логін/2FA).
**[баг]** — 11. **[лікується правилом]** — 5. **[лікується пам'яттю]** — 3.

Найважливіші баги, знайдені під час дослідження:

- **F3 (критичний).** `survey_agent.py:413` викликає `bump_rule_outcome(applied_rule_ids, outcome)`
  без `run_id`. За порожнього `run_id` рядок у `rule_applications` не пишеться
  (`persona_graph_memory.py:578-582`), а `auto_promote_rules` вимагає
  `COUNT(DISTINCT run_id) >= 3` саме з цієї таблиці (`:613-618`). Автопромоція правил
  недосяжна в продакшені. Тести передають `run_id` явно, тому дефект зелений на CI.
- **F9.** Виняток у `vision.decide_action` підставляє `{"action": "wait"}`
  (`survey_agent.py:298-300`), а `"wait"` не оброблено в диспетчері дій → `unknown_action` →
  `break`. Один тайм-аут проксі завершує прогін.
- **F10.** Весь блок `verify_step` під `except Exception: pass` (`survey_agent.py:332-333`):
  недоступний тутор = тихий автономний режим без сигналу оператору.
- **F14.** `record_fact` у продакшн-шляху не викликається взагалі — канал «реальних відповідей»
  наповнюється лише сідом і CLI.

### G3 — PASS

Відповідь однозначна: **міст A→B існує, але в продакшені майже не працює.**

- Канал фактів: читається (`persona_graph_memory.py:1141`, `:1145`), не пишеться (F14).
- Канал правил: читається (`survey_agent.py:77` → `:1159`), але тільки `status='active'`
  і тільки за `host_gates.playbook_mode='active'` (`:1183`); інакше — лише shadow-лог (`:1187`).
- Шлях shadow→active автоматично не існує (F3); працює лише ручний.

Практичний висновок: без двох ручних дій людини на кожен хост накопичене знання не впливає на
жоден наступний прогін.

## Що має зробити координатор (план виправлення FAIL)

Виконати на .184 або Oracle, де є gitnexus, мережа й `~/llm-switch.sh`:

```bash
# G0
node .gitnexus/run.cjs analyze          # або: npm i -g gitnexus && gitnexus analyze
# зафіксувати кількість проіндексованих файлів

# G5
bash bin/ui_verify.sh     ; echo "ui exit=$?"
bash bin/deploy_verify.sh ; echo "deploy exit=$?"
bash bin/ops_verify.sh    ; echo "ops exit=$?"

# G6 — базовий прогін ДО рефакторингу
bash ~/llm-switch.sh survey arno <survey_url> -f
# записати: кількість кроків, stop_reason, outcome з run_traces
```

Після цього — рішення щодо застосування R1–R3 (`sdd-022-pipelines.md`, розділ Implementation),
кожен пункт із попереднім `impact({target: ..., direction: "upstream"})` і фінальним
`detect_changes()`, як вимагає `CLAUDE.md`.

Окремим рішенням координатора: чи виправляти дефекти F3/F9/F10/F14 — вони змінюють поведінку
прогону й тому не можуть увійти в 022 разом із гейтом G6. Пропозиція: винести у Feature 023
з власними гейтами.
