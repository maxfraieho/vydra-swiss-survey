# Методика навчання агента (HITL) — три учасники

Статус: методика затверджена власником 2026-08-10, на основі дослідження Opus-агента
(GitNexus-навігація по коміту `270da66`). Технічна реалізація частини кроків ("Замкнути
цикл") ще в роботі — див. розділ "Стан реалізації" внизу.

## Проблема, яку методика вирішує

Поточний стан (виявлено дослідженням, перевірено на живих даних БД): цикл навчання
**записує, але не діє**. Людина коригує крок агента через `override_step` → рядок
з'являється в `host_rules` → і на цьому все. `host_gates` порожня, `playbook_mode`
завжди `shadow`, `bump_rule_outcome()` не викликається ніде — жодне правило не
потрапляє назад у промпт агента, жодне не отримує підтвердження "спрацювало/ні".

Методика нижче — не про UI. Вона про те, **хто що робить і коли**, щоб корекція
людини реально ставала знанням агента, а не просто рядком у таблиці.

## Три учасники, три темпи

| Учасник | Темп роботи | Роль |
|---|---|---|
| **Агент (Gemma)** | секунди — синхронно з людиною під час кроку | пропонує дію, виконує, фіксує трейс і власний outcome |
| **Q (людина)** | сесія — рішення в моменті + фінальні Approve пізніше | Approve/Correct живого кроку; фінальне рішення про кожну запропоновану Claude нормалізацію; вмикає гейт хоста |
| **Claude** | хвилини, **асинхронно, поза живим кроком** | нормалізує вільний текст у структуроване правило, шукає дублі/конфлікти, пояснює реальний вплив, чистить базу, ремонтує сам цикл |

**Ключове обмеження:** Claude ніколи не стоїть у синхронному шляху HITL. У `verify_step`
є жорсткий дедлайн 300с — будь-яке звернення до Claude всередині цього вікна ризикує
його спалити і зіпсувати оплачуване опитування. Claude працює **після** кроку/прогону,
не під час.

## Цикл: чотири фази

```
ФАЗА 0 — Підготовка (Q + Claude, до прогону)
   Claude читає: GET /api/rules?host=X, /api/rules/conflicts, /api/gate/X, /api/traces?host=X
   Claude віддає: карту покриття — що хост уже вміє, що чекає рішення, що конфліктує,
                  що мертве (hits=0 при значному віці)
   Q вирішує: що вмикати цей прогін, режим гейта хоста

ФАЗА 1 — Живий крок (Агент + Q, синхронно)         ← Claude тут немає
   Агент: vision.decide_action → POST /api/survey/verify_step
   Q: Approve → approve_step  /  Correct → override_step {action, target, value, explanation}
   Корекція пишеться як сирий сигнал (status='shadow'), прогін продовжується одразу

ФАЗА 2 — Розбір (Claude + Q, після прогону)         ← основна робота Claude
   Claude читає сирі корекції прогону + трейс + наявні правила, для кожної віддає:
     • нормалізоване правило {pattern зі словника, behavior, scope, persona, confidence}
     • перевірку дублікатів/конфліктів/суперечності фактам персони
     • diff промпту "до/після"
     • згруповані пропозиції (кілька схожих корекцій → одне правило)
   Q: один клік Approve / Edit / Discard на кожну пропозицію

ФАЗА 3 — Застосування і підкріплення (Агент, наступні прогони)
   Правило active + гейт хоста active → потрапляє в промпт
   Прогін фіксує, які правила застосовувались (rules_used)
   bump_rule_outcome(rules_used, outcome) → wins/losses → авто-промоція/авто-ретір
   Claude періодично (санітарний прохід) чистить мертве і суперечливе
```

## Ролі Claude — конкретно, з прив'язкою до API

Не абстрактний "помічник". Шість функцій, п'ять із них асинхронні, поза критичним шляхом.

**C1. Нормалізатор.** Вхід: `explanation` з `override_step` + `pending_pattern` +
`pending_page_text` + `pending_decision`. Вихід: `{host, persona, pattern, behavior,
confidence, status}` для `POST /api/rules`. `pattern` обов'язково зі словника
(`GET /api/rules/vocabulary`) — інакше `reflection.detect_pattern` ніколи не зматчить
і правило мертве від народження. Це найчастіша можлива людська помилка — саме її
ловить Claude.

**C2. Детектор дублів/конфліктів до запису.** `GET /api/rules?host=&persona=&q=` +
`GET /api/rules/conflicts`. Питання перед створенням: чи є вже правило на цей
`(host, persona, pattern)`? Чи створить конфлікт (різний `source` + різний `behavior`)?
Чи не суперечить факту персони (факти мають вищий пріоритет у промпті)?

**C3. Пояснювач реального впливу.** Показати, як зміниться промпт. Потребує нового
ендпоінта `GET /api/persona/preview?profile=&url=` (тонка обгортка над
`get_enhanced_persona`). Claude робить diff і чесно пише: "гейт хоста = shadow →
це правило НЕ вплине ні на що" — саме ця інформація сьогодні ніде не видна.

**C4. Пакетний аналітик патернів.** Після 5-10 корекцій: шукає повторювані сюжети
(тричі виправляли один патерн → одне правило замість трьох; правило працює на
кількох хостах → підняти scope до `*`). Вихід: `POST /api/rules/bulk` або кілька
`POST /api/rules`.

**C5. Санітар бази.** Періодично: мертві правила (hits=0 при віці), стабільно
програшні (losses > wins), правила з pattern поза словником, правила без evidence.
Вихід: пропозиція `bulk retire` на один клік Q.

**C6. Інженер самого циклу.** Унікальна роль — ні агент, ні Q не можуть полагодити
розімкнуту петлю. Це роботи типу "з'єднати `bump_rule_outcome`", "збудувати екран
гейта", "виправити ключ персони". **Має бути виконано першим** — без цього решта
методики описує машину без приводу.

**Чого Claude не робить:** не приймає рішень у Фазі 1, не промотує правила в `active`
без явного Approve від Q, не вмикає гейт хоста сам. Пропонує — Q підтверджує. Усі
мутації йдуть через `_actor_from_request()` і лишають слід у `rule_audit`.

**Технічна деталь:** якщо пропозиції Claude писати окремим `source` (наприклад
`claude_proposal`), його треба додати в `source_rank` (`persona_graph_memory.py:323`),
інакше він отримує ранг 3 — нижче за `self_reflection` — і програє при дедуплікації.
Безпечніша альтернатива без зміни гарячого шляху: `source='human_override'`,
`status='shadow'`, маркер ролі "пропозиції" — у `note`/`evidence`.

## Стан реалізації

Замикання циклу (C6, найвищий пріоритет) в роботі: `/gate/:host` екран,
`bump_rule_outcome` підключення, `rules_used` атрибуція, `run_id` у evidence —
делеговано на `.161` (agy), відстежується з головної сесії, не запушено в master
до перевірки. Профільний баг `annette`→`annet`, що блокував запуск другої персони,
виправлено і задеплоєно (коміт `9b30559`).

Наступні кроки інтерфейсу (Фаза 1 UI: показ pattern/gate-статусу в `SurveyOps.tsx`,
місток "оформити як правило", добудова `RuleDetail`/`Conflicts`/`RulesTable` до вже
готового API) — заплановані, не почато.

`/legacy` — не видаляти, доки перший живий прогін не пройде через `/ops` з активним
гейтом хоста (умова власної документації `pipeline-and-interface.md`, ще не виконана:
`run_traces` = 0 рядків станом на дослідження).
