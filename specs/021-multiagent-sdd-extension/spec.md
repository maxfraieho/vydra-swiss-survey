# Spec — 021-multiagent-sdd-extension

> **Фіча:** розширення наявного SDD-workflow на Codex CLI, формалізація AGY,
> усунення фантомних `/speckit.*` посилань, введення LLM-арбітра.
> **Гілка:** `astryx-ui-refactor`
> **Статус:** DRAFT

## Контекст і мотивація

Проєкт має зрілу SDD-інфраструктуру (`.specify/constitution.md`,
`docs/for-agents/sdd-development-methodology.md`, `/sdd:*` команди для
Claude Code), але:

1. Конституція §3 нормативно посилається на `/speckit.specify` →
   `/speckit.plan` → `/speckit.tasks` → `/speckit.implement` — команди, яких
   **фактично не існує** в жодному агентному середовищі репо (перевірено
   живим SSH-аудитом dev-184, 2026-08-17).
2. Codex CLI (вже встановлений на dev-184, `codex-cli 0.124.0`) не має
   жодної SDD-інтеграції — працює "наосліп", без посилання на методологію.
3. Документація (`README-sdd-commands.md`) чесно визнає невизначеність щодо
   AGY — дослідження цю невизначеність зняло, документація застаріла.
4. Немає машинно-читного трекера активної фічі (`feature.json`) — контекст
   передається між агентами лише через git log + прозовий `HANDOFF.md`, що
   вже застарів на ~3 тижні на момент аудиту.
5. Немає автоматичної перевірки відповідності коду специфікації —
   підтверджений spec-drift існує вже зараз (коміти посилаються на
   неіснуючий `specs/023-*`).

## User Stories

### US-1: Codex CLI виконує SDD-фічу без ручного копіювання методології

**Given** розробник відкриває Codex CLI в корені `vydra-swiss-survey`
**When** він вводить `/sdd-feature <назва> — <опис>`
**Then** Codex читає `.agents/skills/sdd-feature/SKILL.md`, слідує тим самим
5 крокам, що й Claude Code (`/sdd:feature`), створює
`specs/<NNN-slug>/{spec.md,plan.md,tasks.md}` без дублювання тексту
методології у власному prompt-файлі.

### US-2: AGY-агент має підтверджений, а не гіпотетичний, шлях виконання

**Given** оператор працює через AGY (телефон/AGY2/AGY3)
**When** AGY завантажує метадані скілів на старті сесії
**Then** `/sdd-feature`, `/sdd-bugfix`, `/sdd-refactor`, `/sdd-integration`,
`/sdd-teaching` видимі в TUI як окремі команди (не один загальний
`sdd-workflow` без маршрутизації), кожна семантично парсить аргументи без
`$ARGUMENTS`-підстановки.

### US-3: Конституція не бреше про неіснуючі команди

**Given** новий агент (людина чи AI) вперше читає `.specify/constitution.md`
**When** він доходить до §3 (SDD Workflow)
**Then** описані команди реально виконувані в поточному стані репо — або
через native Spec Kit (`/speckit.*`, встановлений `specify integration
install`), або через задокументований мапінг на `/sdd:*` project-команди.
Жодних посилань на неіснуючі entry points.

### US-4: Агент, що бере фічу в роботу, точно знає її поточну фазу

**Given** два різні агенти (напр. Claude Code і Codex) працюють над проєктом
у різний час
**When** другий агент починає сесію
**Then** він читає `.specify/feature.json`, бачить `branch`, `phase`,
`spec_dir` активної фічі, і якщо `branch` у файлі не збігається з поточною
гілкою — зупиняється і повідомляє оператора, замість припущень з пам'яті.

### US-5: Комміт, що порушує активну специфікацію, блокується автоматично

**Given** розробник (людина чи агент) стейджить зміни, що суперечать
`spec.md`/`plan.md` активної фічі
**When** виконується `git commit`
**Then** `.githooks/pre-commit` викликає `scripts/sdd_llm_judge.py`, який
звіряє diff зі специфікацією через LLM-проксі (`192.168.3.184:18880`) і
блокує коміт (`exit 1`) з переліком порушень — АБО, якщо проксі недосяжний,
пропускає коміт з попередженням (fail-open), не блокуючи розробку через
інфраструктурну нестабільність.

### US-6: `sdd_verify.sh` не падає між гілками

**Given** `bin/sdd_verify.sh` виконується на будь-якій з гілок (`master`,
`astryx-ui-refactor`, майбутній `termux-sync`)
**When** набір `specs/` на цій гілці відрізняється від хардкодженого
allowlist-у
**Then** скрипт динамічно обходить наявні `specs/*/` замість падіння на
відсутніх директоріях, і підтримує режими `--gate` (валідація лише активної
фічі за `feature.json`) та `--arbiter` (виклик LLM-судді).

## Інваріанти, що застосовуються

- **Інваріант 1 (PII):** ключ арбітра — лише в
  `~/.vydra-survey-profiles/sdd_judge.env`, ніколи в git. Diff, що
  надсилається на проксі, виключає `specs/`, `.txt`, `credentials.json`,
  `*.db`.
- **Інваріант 2 (Hot Path <5ms):** НЕ застосовується до pre-commit hook —
  явно поза `survey_agent.py`/`get_host_rules()`, офлайн git-операція.
- **Інваріант 5 (заборона прямого push у `master` з dev-184):** ця фіча
  розробляється і комітиться на гілці `astryx-ui-refactor` (не `master`).
  Жодна фаза цієї фічі не пушить у `master`.

## Явно поза межами цієї фічі (Out of Scope)

- Портування 4 додаткових команд (`clarify/research/audit/verify`) у Codex
  — окрема дельта-задача після підтвердження базового механізму.
- Файловий лок для конкурентного доступу до `feature.json` (race між
  агентами) — тільки advisory-правило в цій фазі.
- Перегляд самого Інваріанту 5 / статусу Termux-контуру — поза скоупом,
  користувач лише уточнив, де фізично тестувати P5, конституцію в цій
  частині не чіпаємо.
- Виправлення знайденого spec-drift "023" — фіксується як окрема майбутня
  задача `/sdd:audit`, не частина цієї фічі.

## Ризики (детально — `plan.md` §7.1)

- R3: жива прод-система на порту 5005 — жодна фаза коду/БД не чіпає.
- R5: нестабільність LLM-проксі — арбітр fail-open.
