## 1. Формат ADR

**Рішення: MADR v3.x** (не спрощений Nygard).

Обидва дослідження одностайні: MADR примушує явно перелічити `Considered
Options` (з pros/cons) та `Decision Drivers` — для AI-агента як автора це
жорсткий промпт-каркас, що запобігає прийняттю першого згенерованого варіанта
без розгляду альтернатив і "переоткриттю" вже відкинутих підходів у пізніших
фічах. Nygard достатній для людини-автора швидких нотаток, але агенти в
ньому систематично пропускають аналіз trade-off'ів.

## 2. Нумерація ADR

**Рішення: наскрізна глобальна нумерація в `docs/adr/NNNN-slug.md`**, НЕ
прив'язана до `specs/NNN-*`.

`specs/NNN-*` мають локальний життєвий цикл фічі (фіча закривається, код
переписується). ADR — глобальний інваріант системи на суцільній часовій осі;
прив'язка до фічі ламає хронологію та ускладнює перехресне скасування
(`ADR-0012 supersedes ADR-0003`, де 0003 народився в іншій фічі). Зв'язок
реалізується через метадані, не через директорійну структуру: у YAML
frontmatter ADR — поле `spec: specs/NNN-slug`; у `spec.md` — рядок
`Reference: ADR-NNNN`.

## 3. log4brains

**Рішення: НЕ інтегрувати зараз.**

log4brains (Next.js CLI, команди `init`/`new`/`preview`/`build`, вбудована
MADR-підтримка з коробки, генератор статичного сайту з historical timeline +
supersedes-графом) технічно підтримує MADR "з коробки", але додає Node.js
build-залежність в CI/CD, що вже й так живе на Termux/Linux мосту без
чіткої потреби. У нас уже є власний Python EPUB-пайплайн
(`~/projects/resume/kindle_digest.py`) — дублювати генератор сайту немає
сенсу. Переглянути це рішення, якщо з'явиться окрема вимога на
публічний/командний ADR-портал (не для одного оператора+агентів).

## 4. Реактивне документування (doc-drift detection)

**Рішення: розширити наявний `scripts/sdd_llm_judge.py` (вже fail-open,
shadow-mode з P8) — НЕ новий окремий сервіс.**

Патерн з обох досліджень: pre-commit/CI arbiter звіряє git diff коду проти
`spec.md`/`docs/adr/*.md`; при виявленні дрифту (напр. зміна сигнатури API,
зміна порогу `auto_promote_rules`) LLM не блокує, а формує чернетку
оновлення ADR/spec.md у режимі пропозиції — вимагає підтвердження оператора
перед застосуванням. Це напряму узгоджується з Інваріантом 3 конституції
(HITL Precedence — рішення оператора завжди мають пріоритет над висновком
моделі) — арбітр лишається дорадчим, не автономним редактором.

## 5. Структура "видань" книжки (ГОЛОВНЕ питання)

**Рішення: Варіант А — Incremental Delta Digest.**

З трьох запропонованих варіантів (A — дайджест змін першим розділом; B —
inline diff-анотації по всій книжці; C — два окремих EPUB, Delta + Full
Reference) обираємо A: перший розділ кожного видання —
`"Edition N: What Changed Since Last Release"` зі списками New/Changed ADR
(2-3 речення з Decision Outcome кожного), Superseded/Deprecated ADR, Modified
Spec Capabilities; далі йде повний актуальний корпус. Причина вибору саме A
над B/C: A дає оператору 3-хвилинне читання перших сторінок на E-Ink для
повного оновлення контексту, без дублювання інфраструктури (на відміну від
C — два build-таски) і без погіршення читабельності чорно-білого екрана
дрібними inline-мітками (на відміну від B). Реалізується як нова секція в
наявному `kindle_digest.py` (`build_briefing()` вже існує — розширюється
джерелами з `docs/adr/` і `specs/*/spec.md` git-діапазону, не переписується
з нуля).

## 6. Критерій "архітектурно значуще рішення, варте ADR"

**Рішення: явний чекліст у `.specify/constitution.md` §3 (не судження
агента "на око").**

ADR обов'язковий, якщо рішення відповідає ХОЧА Б ОДНОМУ з:
1. Впливає на нефункціональні характеристики (безпека, продуктивність,
   стабільність з'єднання/детермінізм hot-path).
2. Дорого відкотити (вибір СУБД/мови/протоколу/структури графа пам'яті).
3. Існує 2+ життєздатних альтернативи з реальними trade-off'ами.
4. Змінює межі/контракт між підсистемами (Flask API ↔ browser agent,
   формат `rule_applications`).
5. Встановлює новий системний інваріант для розробників/агентів (напр.
   зміна порогу `N ≥ 3` з Інваріанту 4).
Локальна деталь реалізації фічі (одне поле, один ендпоінт без зміни
контракту) — лишається в `spec.md`, ADR не потрібен.

## 7. Ретроактивна документація вже прийнятих рішень

**Рішення: тільки baseline, не повна архівна реконструкція.**

Спільнота одностайно проти "ADR-археології" (десятки ретроактивних записів
на кожну дрібницю). Робимо один `docs/adr/0001-baseline-architecture.md` зі
статусом `Accepted (Retroactive)`, що фіксує поточний стек (Flask/Termux
backend, SQLite WAL, прямий CDP замість Selenium, Astryx design system) як
відомі, свідомо прийняті обмеження. Надалі — принцип On-Touch: окремий
ретро-ADR пишеться лише коли фіча реально торкається старої неочевидної
зони і виникає питання "чому це було зроблено так". Це також запобігає
спробі AI-агента "порефакторити" фундаментальне рішення, не розуміючи
вихідних обмежень.

## Відкрите питання для plan.md

Чи виносити ADR-крок в окремий 10-й project-шаблон `/sdd:adr`, чи залишити
підкроком всередині Feature/Refactor/Integration (Plan-фаза перевіряє

ДРУГОГО варіанта (без нового шаблону) — уникнути передчасної абстракції
(один шаблон на 10-й пункт методики поки не виправданий трьома реальними
кейсами) — але це рішення явно виношу в `plan.md` на підтвердження
оператора, а не фіксую тут одноосібно.
