# Specs 022 — Інтеграція ADR (Architecture Decision Records) у SDD-методику

## Мета

Ввести ADR як формальний артефакт SDD-методики для фіксації АРХІТЕКТУРНИХ рішень (чому обрано підхід, які альтернативи відкинуто, які наслідки) — окремо від `spec.md` (що) і `plan.md` (як технічно, швидко застаріває). Реструктурувати процес розробки так, щоб архітектурно значущі рішення трасувались до інваріантів `.specify/constitution.md`.

## Проблема / мотивація

Поточна методика (9 шаблонів, `docs/for-agents/sdd-development-methodology.md`) фіксує specify→clarify→plan→tasks→implement→verify, але немає місця, де фіксується САМЕ РІШЕННЯ і ЧОМУ, окремо від `plan.md`. Конституція фіксує стабільні ІНВАРІАНТИ, але без механізму як туди потрапляють нові інваріанти і на якій підставі. ADR — проміжна ланка: "разове архітектурне рішення в межах фічі" → (якщо стабільне) → "довгостроковий інваріант конституції".

## Given-When-Then сценарії

**Сценарій 1 — рішення під час Plan-фази**
Given: агент виконує `/sdd:feature` або `speckit-plan` для фічі, що вимагає вибору між архітектурними підходами.
When: рішення прийнято.
Then: створюється `docs/adr/NNNN-<slug>.md` (Status/Context/Decision/Consequences); `plan.md` посилається на ADR замість дублювання обґрунтування.

**Сценарій 2 — ADR стає інваріантом**
Given: ADR показав стабільність (пережив N фіч без перегляду / критичний для безпеки чи детермінізму).
When: оператор чи агент підіймає рішення в конституцію.
Then: `constitution.md` отримує новий інваріант з посиланням `[[ADR-NNNN]]`; сам ADR лишається як історичний запис (не видаляється).

**Сценарій 3 — ADR застарів**
Given: нове рішення суперечить попередньому ADR.
When: створюється новий ADR.
Then: старий позначається `Status: Superseded by ADR-NNNN`; жоден ADR не редагується заднім числом (append-only, як git history).

**Сценарій 4 — трасування у feature.json**
Given: фіча зачіпає/створює ADR.
When: `sdd_verify.sh --gate` перевіряє фазу.
Then: `feature.json` отримує ОПЦІОНАЛЬНЕ поле `adr_refs: ["NNNN", ...]` — не required, не блокує gate якщо відсутнє (не кожна фіча вимагає ADR).

## Інваріанти конституції, які МУСЯТЬ бути враховані

- §3 Правило пріоритету: конституція > методологія > транспорт. ADR — НЕ новий шар пріоритету, а джерело кандидатів для оновлення конституції, ніколи не суперечить чинним інваріантам напряму.
- Інваріант 5 (заборона прямих пушів на dev-184 master): ADR-файли комітяться на робочу гілку як будь-який інший файл.
- Нуль рантайм-впливу: чисто документаційний шар, не чіпає hot-path/WAL/HITL інваріанти.

## Межі застосування (Out of scope цієї фічі)

- ADR НЕ замінює `plan.md` (план — тактичне "як", ADR — стратегічне "чому").
- ADR НЕ обов'язковий для кожної фічі — лише для архітектурно значущих рішень (критерій значущості — питання для clarify).
- Без окремого tool/UI перегляду ADR у цій ітерації — прості markdown-файли в git.

## Відкриті питання → clarify.md

1. Формат ADR: MADR (Markdown Architectural Decision Records) чи спрощений Nygard-формат (Context/Decision/Status/Consequences)?
2. Нумерація: наскрізна глобальна (0001, 0002…) чи прив'язана до `specs/NNN-*`?
3. Критерій "архітектурно значуще" — явний чекліст чи судження агента в Plan-фазі?
4. Окремий 10-й project-шаблон `/sdd:adr`, чи ADR — підкрок всередині Feature/Refactor/Integration?
5. Ретроактивна документація вже прийнятих рішень (чому SQLite WAL, чому прямий CDP а не Selenium, чому Astryx design system) як ADR-0001..000N — робити чи ні?
