## 1. Короткий висновок

Astryx у проєкті присутній лише як **компілятор теми**: `npm run theme:build` збирає `src/theme/neutralTheme.ts` у `src/theme/theme.css` (563 рядки згенерованих токенів і `@layer astryx-theme`), `main.tsx` імпортує `reset.css` + `astryx.css` + `theme.css` і обгортає застосунок у `<Theme>`. На цьому все й закінчується — **жоден із 18 екранів не імпортує жодного компонента Astryx**. Виміряні показники за метриками Vibe Testing катастрофічні: **System Ratio = 0 %** (526 блоків `style={{}}` на сирих `<div>`/`<span>`/`<table>`/`<input>`/`<button>`, нуль нативних компонентів), **Token Efficiency = 0 %** (654 хардкоджені HEX-кольори, **жодного** входження `var(--…)` у TSX). Тобто вся згенерована тема — мертвий вантаж: застосунок малює власну палітру `#020617`/`#0f172a`/`#1e293b`, яка не має нічого спільного з токенами `neutralTheme`.

**Головна причина мобільних багів — не Astryx і не каскад, а фіксовані піксельні колонки CSS Grid у master-detail розкладках.** `RulesTable.tsx:199` (`1fr 420px`), `Traces.tsx:128` (`1fr 450px`), `PersonasPanel.tsx:108` (`320px 1fr`) та `PersonasPanel.tsx:259` (`1fr 1fr 120px`) не мають жодної перевірки ширини екрана: щойно користувач відкриває деталь правила чи прогону на телефоні 360–430 px, мінімальна ширина контенту стає ~800+ px, сторінка отримує горизонтальний скрол, а `StatusBar`/`Nav` (шириною 100 % в'юпорта) обрізаються при прокрутці вбік. Наявний хук `useIsNarrow` (480 px) використовується лише в 5 місцях із 22 — три файли оболонки, `MermaidTree` та `SurveyOps`; усі решта екранів адаптивності не мають взагалі. Другий за вагою чинник — розміри клік-зон: типові кнопки/поля мають `padding: '4px 8px'`…`'6px 14px'` при `fontSize: 11–13px`, тобто висоту ~24–30 px замість гарантованих Astryx **44 px** мінімальної зони дотику. Astryx закриває обидві категорії багів «з коробки» (`AppShell` + `MobileNav` для каркаса, вертикальний ритм 28/32/36 px з 44 px клік-таргетом для контролів), але ним не користуються.

## 3. Перевірка `@layer`-каскаду

**Формального бага issue #3755 у проєкті немає, але захисту від нього теж немає — і є гірша, системніша проблема.**

Що встановлено фактично зі зібраного бандла `web/dist/assets/index--1R9_B5o.css` (152 KB):

1. **Немає жодної декларації порядку шарів.** Пошук `@layer <a>, <b>, …;` по бандлу дає нуль збігів. Порядок визначається виключно порядком **першої появи** блоків, тобто порядком імпортів у `web/src/main.tsx:5-7`. Усього в бандлі **5 блоків `@layer` із 3 унікальними іменами**:
   - зсув 0 — `@layer reset` (з `@astryxdesign/core/reset.css`)
   - зсув 2 574 — `@layer astryx-base` (з `astryx.css`)
   - зсув 136 369 — `@layer reset` (другий блок, повтор)
   - зсув 137 604 — `@layer astryx-theme` (з `src/theme/theme.css`)
   - зсув 152 044 — `@layer astryx-theme` (другий блок, повтор)

   Повтори на порядок не впливають (він фіксується першою появою), тож відносний порядок трьох шарів **випадково правильний** і зараз нічого не ламається. Але це крихка конструкція: будь-який новий CSS-імпорт, доданий у `main.tsx` вище рядка 5, або майбутнє підключення Tailwind/CSS-модулів мовчки перевпорядкує каскад. Шарів `components` і `utilities` не існує взагалі.

2. **Нешарованих (unlayered) CSS-правил у бандлі немає** — усі 152 KB лежать усередині трьох шарів. З боку CSS проєкт чистий.

3. **Реальний обхід каскаду — не CSS, а inline-стилі.** 526 блоків `style={{}}` у TSX мають пріоритет вищий за **будь-який** `@layer`, включно з `astryx-base`. Зараз це нешкідливо (компонентів Astryx нема, перебивати нічого), але це **міна під міграцію**: щойно перший `<Button>` чи `<Card>` з'явиться всередині обгортки з `style={{}}`, поведінка стане саме тією, що описана в issue #3755 — компонент мовчки втратить внутрішні відступи/межі, без помилок у консолі. NotebookLM це підтверджує окремо: inline-стилі «діють поза каскадними шарами, які критично важливі для правильного застосування стилів Astryx на мобільних пристроях».

4. **`web/index.html:9`** — `<body style="margin: 0; background: #020617;">`. Класичний випадок: inline-стиль на `<body>` перебиває фон теми з `light-dark()`, через що zero-flash-механізм перемикання світлої/темної теми фізично не може спрацювати. Прибрати разом із етапом 0.

5. **`@astryxdesign/theme-neutral/theme.css` не імпортується** — і це **правильно**. NotebookLM підтвердив: згенерований `astryx theme build` CSS самодостатній (містить власні токени + успадковує дефолти системи), окремий імпорт базової теми не потрібен; обов'язковим лишається тільки `@astryxdesign/core/reset.css` у найнижчому шарі — він у `main.tsx:5` є. Тобто пакет `@astryxdesign/theme-neutral` у `package.json` лишається як peer-джерело дефолтів для збірки теми, а не як runtime-імпорт.

**Рекомендована дія (етап 0):** створити `web/src/styles/layers.css` з єдиним рядком декларації й імпортувати його **першим** у `main.tsx`, перед усіма іншими CSS:

```css
/* web/src/styles/layers.css — має імпортуватись першим */
@layer reset, theme, base, astryx-base, astryx-theme, components, utilities;
```

```tsx
// web/src/main.tsx
import './styles/layers.css';          // ← новий, обов'язково перший
import '@astryxdesign/core/reset.css';
import '@astryxdesign/core/astryx.css';
import './theme/theme.css';
```

## 4. Поетапний план міграції

Порядок узгоджений з офіційною послідовністю Astryx («міграція каркаса, а не точкова заміна тегів; завжди починати з app frame, не з окремих кнопок»), але **перед нею вставлено етап 1** — бо він за кілька годин прибирає ~80 % скарг на мобільне відображення без жодного нового компонента й без ризику зачепити каскад.

### Етап 0 — Фундамент каскаду (0.5 дня, 3 файли)
1. Створити `web/src/styles/layers.css` з декларацією порядку шарів; імпортувати першим у `web/src/main.tsx`.
2. Прибрати `style="margin: 0; background: #020617;"` з `web/index.html:9`.
3. Виконати `npx astryx doctor` — `web/node_modules` на цьому хості **присутній**, але перевірку версії Node (≥22.13.0), синхронізації `core`/`cli` та peer-залежностей ще ніхто не проганяв. Вимога `package.json` `"node": ">=26.4.0"` (+ `"npm": ">=11.19.0"`) теж потребує звірки з реальним рантаймом деплою.
4. Смоук-тест: тимчасова сторінка з `<Button>`, `<TextInput>`, `<Card>` — переконатись, що відступи не зникли (це і є перевірка на #3755).

**Результат:** міграція стає безпечною. Видимих для користувача змін немає.

Найшвидший шлях до працездатного телефону. Прибрати фіксовані піксельні колонки, використавши вже наявний `useIsNarrow`:

Плюс, у тих самих 4 файлах, підняти клік-зони кнопок дій до `min-height: 44px` (проміжне рішення до переходу на `Button`). Форми `1fr 1fr` у `HostsPanel`/`PatternsPanel`/`ProvidersPanel`/`RuleComposer`/`RuleDetail` (7 місць) — тим самим прийомом, другою хвилею того ж етапу.

### Етап 2 — Каркас на нативному Astryx (2–3 дні, 4 файли оболонки)
Замінити самописний каркас на `AppShell` + `TopNav` + `MobileNav`:
- `shell/AppShell.tsx` — `<div>`/`<main>` → нативний `AppShell` зі слотами.
- `shell/Nav.tsx` — 8 `NavLink` у flex-`<div>` → `TopNav` + `NavMenu`; на вузьких екранах — `MobileNav`-шторка.
- `shell/StatusBar.tsx` — `Badge` для статусу, `Banner` для HITL-попередження.
- `shell/TokenField.tsx` — `TextInput` + `Button`.

Обов'язково протестувати те, на чому найчастіше ламається саморобна мобільна навігація: перенесення фокусу всередину шторки при відкритті, закриття меню при зміні маршруту, повернення фокуса на кнопку-виклик після закриття. Після цього `shell/useIsNarrow.ts` імовірно стане непотрібним для каркаса (лишиться хіба для `MermaidTree`).

Імпорти — виключно з субшляхів: `import { Button } from '@astryxdesign/core/button';`. Перевірити, що в `web/tsconfig.json` `moduleResolution` = `bundler` або `node16`, інакше субшляхи не резолвляться.

**Результат:** мобільна поведінка (згортання навігації, drawer, адаптивні відступи, фокус-менеджмент) переходить у відповідальність фреймворка. Хаки етапу 1 у каркасі знімаються.

### Етап 3 — Примітиви по екранах (5–8 днів, 18 файлів, сторінка за сторінкою)
Порядок за співвідношенням користь/ризик:
1. `SettingsPage.tsx` → `TabList` (найбільший виграш: 4 копії 18-рядкового inline-стилю зникають одним компонентом).
2. Таблиці — 6 файлів (`RulesTable`, `Traces`, `Compare`, `Conflicts`, `HostsPanel`, `PatternsPanel`, `ProvidersPanel`) → `Table`; на вузьких екранах — `ListItem` замість табличних рядків.
3. Форми — 6 файлів (`RuleComposer`, `BehaviorEditor`, `HostsPanel`, `PatternsPanel`, `ProvidersPanel`, `PersonasPanel`) → `TextInput` / `TextArea` / `Selector` / `Switch` / `Button`. Стан валідації — через status-пропси компонентів, **не** через ad hoc зміну кольору межі.
4. Картки й контейнери — усі екрани → `Card`, `VStack`/`HStack`, `Text`, `Heading`.
5. `ui/Markdown.tsx` + `ui/markdownParse.tsx` (541 рядок власного парсера/рендера) → `Markdown` + `CodeBlock`; кандидат на найбільше скорочення коду в проєкті.

Правило етапу: `<div>`-обгортка заради `margin` — заборонена; відступ ставиться `xstyle` безпосередньо на компоненті. Стилі `:hover` — тільки всередині `@media (hover: hover)`, інакше на тачі ефект «залипає» після дотику.

**Результат:** System Ratio з 0 % до ~70–80 %.

## 5. Питання-відповіді від NotebookLM (notebook «Astryx», MCP `100.113.140.25`)

Підключення успішне, задано два питання.

### Питання 1 — мобільна адаптивність

> Як AppShell реалізує мобільну поведінку; які офіційні responsive-патерни; числові breakpoints; поведінка Table на вузьких екранах; типові баги при обході AppShell.

Ключове з відповіді:

- **`AppShell`** — глобальний адаптивний каркас. На вузьких в'юпортах `SideNav` згортається, навігація переходить у режим мобільної шторки — через `MobileNav` або вбудовану поведінку самого `AppShell`. Обов'язково тестувати керування фокусом, поведінку закриття та обробку зміни маршрутів. **Конкретних пропсів/слотів `AppShell` у джерелах немає.**
- **Responsive-патерни:** офіційна рекомендація — **Tailwind CSS через проп `className`** (система постачає CSS-міст, що мапить токени на класи Tailwind). Якщо стилізація через `xstyle` — медіа-запити пишуться всередині `stylex.create()`. **Адаптивних пропсів-об'єктів (`{sm:…, md:…}`), хуків `useBreakpoint`/`useMediaQuery` та компонента `Grid` з адаптивними колонками в джерелах немає.**
- **Числові breakpoints у джерелах не вказані.** → Для нашого плану це означає: власний `useIsNarrow(480)` лишається легітимним інструментом на етапі 1, і його не буде чим замінити «офіційно» до етапу 2.
- **Захист від тач-багів:** усі `:hover`-стилі мають бути загорнуті в `@media (hover: hover)`, інакше ховер «залипає» на сенсорних екранах. *(У нашому коді `onMouseEnter`/`onMouseOver` — 0 входжень, тобто hover-логіки в JS немає; ризик низький, але при переході на `xstyle` правило треба тримати.)*
- **`Table` на вузьких екранах:** поведінка самого `Table` не описана (ні горизонтальний скрол, ні card-режим не підтверджені). Рекомендований підхід для мобільних списків — компонент **`ListItem`** (карткоподібні інтерактивні рядки).
- **Типові баги при обході `AppShell`:** (а) порушення безпеки каскадних шарів — нешаровані legacy-скидання перезаписують `@layer astryx-base`, компоненти на мобільних раптово втрачають `padding`/межі; (б) зламане керування фокусом у саморобній мобільній навігації — фокус не переноситься у шторку, меню не закривається при переході, фокус не повертається на кнопку-виклик; (в) залипання станів через сирі елементи замість нативних компонентів із `data-checked`/`data-disabled`; (г) зайві `<div>`-обгортки заради `margin` та `style={{}}` — офіційні антипатерни, які руйнують flexbox-каркас і «розповзаються» на вузьких екранах.

### Питання 2 — міграція наявного React-коду

> Порядок міграції додатку, де всі екрани на сирих div/table/input; точні заміни; формат субшляхів; шкода inline `style`; чи потрібен окремий імпорт `theme-neutral/theme.css`.

Ключове з відповіді:

- **Порядок:** (1) `npx astryx init`; (2) **явно задекларувати порядок `@layer` до першого імпорту компонентів**; (3) смоук-тест з базовими примітивами — перевірка, що відступи не зникли; (4) **першим мігрувати глобальний каркас** (`AppShell` + `TopNav` + `SideNav`), а не окремі кнопки — каркас спільний для всіх маршрутів, тому одразу виявляє глобальні проблеми адаптивності й тем; (5) далі — leaf-компоненти сторінка за сторінкою; (6) наприкінці — глобальні процеси (`CommandPalette`, повери, підтвердження).
- **Мапінг:** `<table>` → `Table` (мобільні списки → `ListItem`); панель → `Card`; поле → `TextInput` (валідація через status-пропси, не через ad hoc CSS); кнопка → `Button`, іконкова → `IconButton`; статус → `Badge` (**`StatusDot` у джерелах не підтверджено**); бічна панель деталей → `Dialog`, деструктивні дії → `AlertDialog` (**`Layer`/`Drawer` у джерелах немає**); сповіщення → `Banner` (в межах сторінки) / `Toast` (тимчасове); **`EmptyState` у джерелах не підтверджено** — є лише вимога тестувати empty/error-стани.
- **Субшляхи:** офіційний і рекомендований формат — `import { Button } from '@astryxdesign/core/button';`. Вимога: `moduleResolution` = `bundler` або `node16` у `tsconfig.json`.
- **Inline `style={{}}`:** офіційний антипатерн. На самих компонентах Astryx проп `style` мерджиться після StyleX і виграє конфлікти, але при цьому (а) діє поза `@layer`, критично важливим для мобільних стилів, (б) обходить build-time дедуплікацію StyleX, (в) змушує хардкодити значення, ламаючи темну тему й перевизначення токенів.
- **`theme-neutral/theme.css`:** окремо імпортувати **не потрібно** — згенерований `astryx theme build` CSS самодостатній, а супутній JS містить прапорець `__built: true`, який каже провайдеру `<Theme>` пропустити runtime-ін'єкцію стилів. Але `@astryxdesign/core/reset.css` у найнижчому шарі `@layer reset` імпортувати **обов'язково** (у нас є — `main.tsx:5`).
